# Data Foundation Architecture (Phase 2)

This document defines the architecture and implementation plan for Phase 2: Data Foundation. It serves as the bridge between the frozen C++ exchange engine and the future AI/Quant Intelligence layer.

## 1. Data Categorization & Separation

Data in the system must be strictly separated based on its source and state to avoid contamination and ensure reproducibility.

### A. External/Historical Data
- **Source:** Real-world market datasets (e.g., CSV dumps, Kaggle datasets, API endpoints like Yahoo Finance or Alpaca).
- **Purpose:** Used for backtesting, model training, and baseline feature engineering.
- **State:** Static, immutable. Once ingested, the raw format is preserved.

### B. Synthetic QuantExchange Data
- **Source:** Simulated orders and events generated by the C++ Matching Engine (e.g., Random Trader, Market Maker bots).
- **Purpose:** Stress testing, scenario simulation, and observing market microstructure effects (e.g., how the book reacts to a large market order).
- **State:** Generated dynamically during simulations, then persisted.

### C. Future Live/Streaming Data
- **Source:** Real-time WebSocket or API feeds (Phase 9+).
- **Purpose:** Feeding the AI Market Assistant and paper trading logic in near real-time.
- **State:** Ephemeral, appended continuously to a time-series store.

---

## 2. Minimum Viable Dataset (Baseline)

Before attempting complex order-book microstructure modeling (Level 2/Level 3 data), the first baseline model requires only:
- **Level 1 Trade/Tick Data:** Timestamp, Symbol, Price, Volume.
- **Aggregated OHLCV (1-minute / 5-minute):** Open, High, Low, Close, Volume.

**Why:** A simple OHLCV dataset is sufficient to build the entire ingestion, cleaning, feature engineering, and model validation pipeline. Once the pipeline is robust, high-resolution order-book depth data can be introduced.

---

## 3. Storage Schema & Normalization

Data will be stored in PostgreSQL (or a dedicated time-series DB in the future), heavily utilizing partitioned tables for performance.

### Raw Market Data (Normalized Schema)
```sql
CREATE TABLE historical_ohlcv (
    timestamp TIMESTAMPTZ NOT NULL,
    symbol VARCHAR(20) NOT NULL,
    open NUMERIC,
    high NUMERIC,
    low NUMERIC,
    close NUMERIC,
    volume NUMERIC,
    PRIMARY KEY (symbol, timestamp)
);

CREATE TABLE historical_trades (
    trade_id BIGSERIAL PRIMARY KEY,
    timestamp TIMESTAMPTZ NOT NULL,
    symbol VARCHAR(20) NOT NULL,
    price NUMERIC NOT NULL,
    quantity NUMERIC NOT NULL,
    is_buyer_maker BOOLEAN
);
```

## 4. Pipeline Architecture

### A. Ingestion Pipeline
- **Extract:** Scripts to read CSV files, query public APIs, or listen to synthetic event logs from the C++ engine.
- **Load:** Insert raw data directly into `raw_` staging tables or raw file storage (e.g., Parquet).

### B. Cleaning & Validation Pipeline
- **Missing Values:** Forward-fill missing prices, zero-fill missing volumes.
- **Outlier Detection:** Flag or remove ticks that deviate beyond a standard threshold (e.g., > 10% move in a single tick).
- **Validation:** Assert strictly monotonic timestamps and non-negative prices/volumes.

### C. Feature-Engine Boundary
- **Input:** Cleaned OHLCV or Trade data.
- **Output:** A materialized view or Parquet file containing derived features (e.g., 14-period RSI, volatility, bid-ask spread). The Feature Engine does *not* train models; it only transforms state.

---

## 5. Machine Learning Infrastructure Strategy

### Time Split Strategy (Train/Validation/Test)
Financial data cannot be randomly shuffled due to time-series leakage.
- **Train:** E.g., Jan 2020 - Dec 2023.
- **Validation:** E.g., Jan 2024 - Jun 2024.
- **Test (Holdout):** E.g., Jul 2024 - Oct 2024.
- **Rule:** The model can never see data from time `t+1` when predicting time `t`.

### Data Versioning & Provenance
Every dataset used for training must be tagged with a unique hash/version (e.g., using tools like DVC or simply versioned Parquet files in a directory `data/v1_ohlcv_2020_2023`).

### Future ML Targets (Do NOT Implement Yet)
Once the data foundation is solid, Phase 4 will target:
1. **Short-horizon return/direction:** Probability of price increase over the next N minutes.
2. **Volatility:** Expected standard deviation of returns over the next N minutes.
3. **Market regime:** Classification (e.g., High-Vol Trending, Low-Vol Mean-Reverting).
4. **Execution/fill probability:** Likelihood of a limit order filling at a specific distance from the mid-price.

## 6. Folder & Module Structure

To ensure the C++ exchange core remains undisturbed, all intelligence tracks will live in a strictly isolated `intelligence/` (or `quant/`) directory.

```
QuantExchange/
├── src/                  # (FROZEN) C++ Matching Engine 
├── include/              # (FROZEN) C++ Headers
├── db/                   # Database schemas
├── tests/                # (FROZEN) C++ Tests
├── intelligence/         # NEW: Data & Quant Track
│   ├── data/             # Raw & processed data storage (ignored in git)
│   ├── ingestion/        # Scripts to fetch and store data
│   ├── cleaning/         # Validation and normalization scripts
│   ├── features/         # Feature engineering logic
│   ├── models/           # Future ML training scripts
│   └── notebooks/        # Jupyter notebooks for EDA and research
```

## 7. Phase 2 Implementation Plan

**Goal:** Build the Data Foundation without touching C++ or ML training.

- **Step 1: Scaffolding**
  - Create the `intelligence/` folder structure.
  - Set up a Python environment (e.g., `requirements.txt` with pandas, sqlalchemy, psycopg2).

- **Step 2: Database Schema Update**
  - Add the `historical_ohlcv` and `historical_trades` tables to PostgreSQL.

- **Step 3: Ingestion Script**
  - Write a Python script to download a sample historical dataset (e.g., 1 year of daily/minute OHLCV data for 3 symbols).
  - Load this raw data into PostgreSQL or Parquet.

- **Step 4: Cleaning & Validation**
  - Write a Python script that pulls the raw data, applies basic data-cleaning rules (handling NaNs, timestamp sorting), and saves it as a "clean" dataset.

- **Step 5: Verification**
  - Validate that the data is queryable and properly isolated from the C++ operational tables.
